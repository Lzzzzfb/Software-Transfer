## 先定义可证明的目标

把“完整、正确、流畅”拆成可测量指标：

| 目标 | 推荐证据 |
|---|---|
| 自动识别 | 候选端口、握手成功、序列号和像素数 |
| 正确解析 | 合法帧数、长度/命令/序号、解析样本 |
| 全帧保存 | 合法接收数与持久化数相等、CRC 或记录计数 |
| 界面流畅 | 发布 FPS、实际绘制 FPS、事件循环延迟 |
| 停止可靠 | 停止 ACK、尾帧静默、进程和导出状态 |
| 断线恢复 | 断线时间、端口重扫、重新握手与恢复结果 |
| 保存正确 | CSV/XLSX 结构、元数据、帧列数、数值抽样 |

明确保证边界：上位机只能保证对操作系统已交付且通过协议结构验证的数据做到最佳接收与持久化；不能恢复 MCU 未发送或在到达应用前已丢失的数据。

## 建立分层指标

不要只报告一个“FPS”。至少分开记录：

1. 串口读取字节率；
2. 解码出的合法帧率；
3. 持久化成功帧率；
4. 显示发布帧率；
5. 实际绘制帧率；
6. 导出吞吐和排队长度。

同时记录累计计数：

- 接收字节；
- 完整帧；
- 持久化帧；
- 长度拒绝；
- 命令拒绝；
- 重新同步；
- 协议序号缺失、重复、乱序；
- 为显示主动跳过；
- 存储队列高水位；
- 导出成功/失败。

只有完整数据通道能判断真实丢帧；经过节流的绘图通道不得参与协议缺帧判断。

## 使用飞行记录器

飞行记录器是低开销、循环覆盖的结构化运行记录。它持续保留最近一段关键证据，在故障发生后导出，而不是把所有原始日志无限写盘。

建议记录：

- 单调时钟和本地时间；
- 会话、设备、端口和线程/进程；
- 状态机转换与原因；
- 命令发送、ACK、超时；
- 分层速率与队列水位；
- 帧序号统计和拒绝原因；
- CPU、内存、温度和磁盘摘要；
- 最近少量原始帧或其十六进制前后缀；
- 未捕获异常和退出原因。

控制开销：

- 高频事件只累加计数，按秒汇总；
- 原始帧只保留固定数量；
- 使用有界内存；
- 不在 GUI 主线程压缩；
- 导出诊断包时冻结快照。

## 生成诊断包

诊断包应支持从用户界面一键生成，并至少包括：

```text
manifest.json
runtime.json
timeline.jsonl
metrics.jsonl
logs/
config/
frame-samples/
checksums.sha256
```

注意隐私和体积：

- 不默认包含全部正式采集数据；
- 配置中敏感路径或凭据脱敏；
- 每个文件记录大小和 SHA-256；
- 生成 ZIP 前先写临时文件，再原子重命名；
- 在清单中记录是否因大小限制而省略内容。

## 诊断常见现象

### GUI 只有几 FPS

按顺序确认：

1. 完整帧率是否仍高；
2. 持久化帧率是否等于完整帧率；
3. 显示发布率和实际绘制率；
4. 实时页与诊断页的 CPU 差异；
5. 主线程是否创建大量 Python 绘图对象；
6. 是否重复触发自动范围、坐标轴重排或曲线重建。

如果采集和存储稳定而实时页 CPU 接近单核，优先优化绘图，不要归因于 USB 或整个 SoC 性能。

### 运行越久越卡

检查：

- 列表、日志、曲线对象或缓存是否无界增长；
- 信号连接是否重复；
- 同一帧是否被多个计时器重复绘制；
- CSV/XLSX 是否在 GUI 线程持续重写；
- 队列是否无界；
- 停止时是否一次性转换全部历史数据。

### 有拒绝帧或重新同步

分别统计拒绝原因，不要只写“校验错误”。核对：

- 数据帧与控制帧是否使用不同长度规则；
- 校验字节是否应消费但不验证；
- 像素值中的 `0x24` 是否被误当作帧头；
- 候选长度是否与已握手像素数一致；
- ACK 是否和数据帧共用安全解析器；
- USB 内核日志是否有重置、断开或溢出。

### 自动存储未勾选却出现缓存文件

区分安全缓存和正式导出：

- `.part`、`.zgs` 等可作为崩溃恢复暂存；
- 正常完成且未启用自动存储时应自动清理；
- 自动导出成功后应清理；
- 失败时保留并在界面明确报告路径；
- 暂存文件不得伪装成用户选择的正式结果。

## 执行性能测试

同时采集应用和系统证据：

```bash
pid="$(pgrep -n -f '/opt/example-app/main.py')"
top -H -b -n 10 -d 1 -p "$pid"
ps -p "$pid" -o pid,stat,pcpu,pmem,rss,vsz,etime,cmd
cat /sys/class/thermal/thermal_zone0/temp
df -h
```

比较至少四种工况：

1. 空闲主界面；
2. 实时绘图；
3. 诊断页；
4. 实时绘图加自动存储。

绘图微基准可使用：

```bash
QT_QPA_PLATFORM=offscreen \
PYTHONPATH=/opt/example-app \
/opt/example-app/.venv/bin/python \
/home/radxa/benchmark_plot_render.py \
--pixels 3648 --width 1400 --height 800 --iterations 30
```

离屏基准用于比较绘图实现，不代表显示器刷新、X11 合成或真实交互延迟。

## 执行数据完整性验收

对一个固定时长会话记录：

- 设备协议序号起止；
- 合法完整帧数；
- 持久化记录数；
- 序号缺失、重复、乱序；
- 应用主动丢弃数；
- 显示主动跳过数；
- 文件内实际帧列数；
- 原始帧或记录 CRC 校验结果。

验收关系：

```text
合法完整帧数 == 成功持久化帧数 + 已明确报告的存储失败帧数
```

显示帧数可以远小于持久化帧数。若协议序号由设备可靠提供，再结合序号判断设备发送链路的可见缺口。

异常强度不能单独证明错误帧。暗场、扣背景、饱和与真实脉冲都可能产生零值、负值或高值。先验证结构，保留可疑数据并附加统计诊断。

## 执行断线与停止验收

停止测试：

1. 在低速和高速采集下分别停止；
2. 记录停止命令和 ACK；
3. 等待规定的尾帧静默；
4. 确认串口读循环和采集进程退出；
5. 确认暂存安全关闭；
6. 允许导出异步收尾；
7. 立即再次开始采集。

断线测试：

1. 采集中拔出 USB；
2. 界面必须进入明确的断开状态；
3. 持久化已接收帧；
4. 停止旧任务并释放句柄；
5. 插回设备；
6. 重新枚举、握手并按序列号匹配；
7. 由产品策略决定自动恢复还是等待用户开始。

不要仅以 `/dev/ttyACM0` 是否再次出现判定重连成功，必须重新完成协议握手。

## 验证导出文件

CSV 验证：

- 编码和分隔符正确；
- 中文标签可读；
- 元数据完整；
- 每帧一列、每像素一行；
- 单设备文件名符合命名规则；
- 不覆盖已有文件。

Excel 验证：

- 工作表数量与设备数量一致；
- 工作表名合法且唯一；
- 每台设备元数据与帧数正确；
- 数值类型未被写成字符串；
- 临时文件在成功后消失；
- 使用库读取所有单元格结构，并在工具可用时渲染全部工作表做视觉检查。

历史页面要兼容既有文件，不应因标签本地化或新增处理方式破坏旧数据读取。

## 形成结论

每个故障用同一模板收口：

```text
现象
证据
排除项
根因
修复
验证结果
通用经验
适用边界
```

不要使用“应该”“感觉”“可能是板子慢”作为最终结论。若证据仍不足，明确列出尚未证明的假设和下一项最小实验。

## 验收矩阵

- [ ] 目标环境、架构、Python、Qt 与依赖版本已记录。
- [ ] 自动识别包含协议握手而非只看串口名。
- [ ] 参数读取与实际设备信息一致。
- [ ] 完整帧率、持久化帧率、显示帧率独立统计。
- [ ] 满负荷运行无无界队列、日志或内存增长。
- [ ] 所有合法应用可见帧均保存，失败有明确计数。
- [ ] 停止后可立即再次采集。
- [ ] 拔插后可重新握手和恢复。
- [ ] CSV/XLSX 内容、命名、不覆盖和本地化均验证。
- [ ] 自动存储关闭时没有残留的正常暂存文件。
- [ ] 自动存储开启时 GUI 仍可操作，导出不阻塞停止。
- [ ] 诊断包可复现关键时间线并包含版本哈希。
- [ ] 部署载荷通过一致性检查。
