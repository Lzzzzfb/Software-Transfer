# ROCK 4B+ 上位机尽力无损采集设计

## 目标与保证边界

目标是在不修改 MCU 协议的前提下，使上位机软件尽可能可靠地接收和保存全部采集数据，同时保持界面流畅。

上位机提供以下明确保证：

> MCU 实际送达 Linux 串口、且能按实机协议恢复为完整合法帧的每一帧，要么成功进入持久化临时文件，要么程序明确报告错误并受控停止；不得因 GUI、绘图、处理或 CSV/Excel 导出负载而静默丢帧。

不保证 MCU 未发送的数据，也不能恢复在到达上位机前已经丢失的字节。当前数据帧 CheckSum 为任意值且不验证，因此只能确认结构、长度、序号和像素数量正确，不能对每个像素值提供端到端校验。

## 已确认的实机协议

SN003、硬件 1.20、固件 2.20 实测参数：

- `nPixel = 3694`
- `nStartPixel = 32`
- `nValidPixel = 3648`
- 数据帧使用 U16LE 包号兼容格式
- `nLength = 3 + 2 * nPixel = 7391`
- CheckSum 不计入 `nLength`
- 物理帧长度为 `4 + nLength = 7395` 字节
- 像素为 U16BE
- 最前 32 个像素裁掉，保留 3648 个有效像素

保留函数表新版 U32 包号格式的兼容能力。每次连接在识别首个合法数据帧后锁定该设备本次会话的协议格式，后续不再同时接受两种数据长度。

## 方案比较

### 方案 A：继续优化当前 QThread

采用 NumPy 直接解析、删除重复信号和定时器，并扩大缓冲。改动较小，但串口线程与 GUI 仍位于同一 Python 进程并争用 GIL，不能从结构上保证高输入速率下不受 GUI 影响。

### 方案 B：独立 Python 采集进程（采用）

独立进程拥有串口、拆包、ACK 和二进制落盘。GUI 只接收最新显示帧和低频诊断。它无需交叉编译原生模块，能够利用 ROCK 4B+ 的其他 CPU 核，并隔离 GUI、处理和导出负载。

### 方案 C：C/C++ 原生采集服务

性能和确定性最好，但需要新的原生构建、ARM64 交叉编译、接口和维护体系。当前约 0.67 MB/s 的实测数据量不需要承担这项复杂度。

## 进程与数据流

### 采集进程

每台设备由一个独立采集进程独占串口。第一阶段只有一台设备，但边界按设备隔离。

采集进程负责：

- 打开和关闭 `/dev/ttyACM0`
- 握手、参数命令、开始和停止命令
- 持续读取原始字节
- 严格拆包、协议格式锁定和序号检查
- 将每个合法帧写入会话临时文件
- 向 GUI 发布最新显示帧
- 向主进程发布 ACK、状态和汇总诊断

控制命令与数据帧在同一串口流中解析，但控制事件不受显示节流影响。

### 持久化主通道

当前位于 `SerialWorker._handle_packet()` 中、解析前的 50 ms 门控必须移到持久化之后。采集进程解析每个完整数据帧，并立即写入轻量二进制会话文件。

会话文件采用顺序追加的记录格式，每条至少包含：

- 记录魔数和格式版本
- 设备标识
- 原始 U16 包号及位宽
- 单调时钟和系统时间
- 总像素数、起始像素和有效像素数
- 3694 个原始 U16 像素，保持固定字节序
- 记录长度和记录级校验，用于检测上位机临时文件损坏

临时文件是采集期间的数据事实来源。正常停止后由现有独立保存进程读取，应用任务开始时冻结的背景、参考、校准和处理模式，再生成 CSV/Excel。按照既有用户决策，最终导出只保留处理后的结果。

采集期间不逐帧重写 XLSX，也不把所有像素对象通过 `multiprocessing.Queue` 传送给 GUI。

### 显示通道

显示通道是有意可丢弃的旁路：

- 采集进程完成持久化后，最多每 50 ms 发布最新一帧
- 队列容量为 1，只覆盖旧显示帧
- GUI 卡顿只降低显示 FPS，不改变持久化帧数
- 绘图、坐标轴、背景扣除预览均在 GUI/处理侧进行

诊断必须分别统计“完整接收帧、已持久化帧、显示帧和显示主动覆盖帧”，不得再用显示帧数代表设备原始 FPS。

## 解析性能

数据帧像素使用 `numpy.frombuffer` 按大端 U16 建立视图，再在持久化或跨进程边界需要时复制。取消每帧 `struct.unpack`、列表、逐点 `int()` 和元组之间的重复转换。

拆包器仍保持：

- 帧头、命令、精确长度检查
- 已锁定协议格式检查
- 已知 `nPixel` 检查
- U16 包序号连续性检查
- 损坏候选逐字节重新同步

数据 CheckSum 按实机约定消费但不验证。

## 异常处理

### 少量异常

以下情况记录后继续：

- 单个包号缺失
- 单次重新同步
- 少量不完整数据帧

不完整帧不进入正常光谱文件。诊断附件保留损坏点前后有界的原始字节、时间、前后包号和解析原因，不保存无限原始噪声。

### 受控停止

默认触发条件：

- 连续 5 个数据帧异常
- 滚动 10 秒窗口内缺失或损坏帧比例达到 5%
- 串口输入缓冲溢出
- 临时文件写入失败
- 可用磁盘空间低于一个明确安全下限
- 采集进程退出或进程间控制通道断开

受控停止顺序：

1. 请求采集进程发送 `0x52`
2. 等待 ACK，并继续接收设备尾部数据
3. 达到静默窗口后封存临时文件
4. 刷新文件并写入会话清单
5. 报告停止原因及数据完整性统计
6. 对已封存的合法帧继续执行异步导出

阈值作为 Linux 专用配置项集中定义，不在 GUI 中增加第一阶段不必要的复杂设置。

## 临时文件可靠性与恢复

- 顺序追加，避免采集期间随机更新大型工作簿
- 定期刷新用户态缓冲区
- 按有界批次执行 `fsync`，兼顾掉电窗口和存储寿命
- 正常封存通过原子重命名产生完成标记
- 异常退出保留 `.part` 和会话清单
- 下次启动只报告和提供恢复，不自动覆盖已有文件

无法承诺突然断电前尚未 `fsync` 的最后一个批次，但不会把未封存文件伪装成完整结果。

## 诊断页

每台设备显示：

- 串口原始字节数
- 完整数据帧数
- 已持久化帧数
- 显示发布帧数
- 显示主动覆盖帧数
- 包序号缺失、重复、回退和回绕
- 拒绝候选数量和重新同步次数
- 当前协议格式、`nPixel` 和物理帧长度
- 临时文件大小、刷新状态和磁盘余量
- 受控停止阈值及触发原因

诊断事件低频汇总后传给 GUI，避免错误日志本身形成事件洪泛。

## 测试

自动测试覆盖：

- U16 实机格式和 U32 新版格式首帧识别及会话锁定
- 任意串口分片下的完整拆包
- 损坏帧后恢复且不把损坏帧写入正常会话
- 每个合法帧恰好写入一次
- GUI 队列阻塞时持久化计数仍连续
- 保存进程繁忙时采集进程仍持续落盘
- 少量异常继续、达到阈值受控停止
- 磁盘失败、空间不足和采集进程退出
- 异常 `.part` 恢复
- 背景扣除后最终仅导出处理结果

板端验收使用自动保存开启的连续采集，至少覆盖不同积分时间和采集间隔。验收比较设备完整帧数、临时文件记录数和最终导出帧数，并在 GUI 高负载下确认三者一致。

## 范围

只修改 Linux 专用副本和 `deploy/rock4bplus`。不修改原 Windows 项目和 MCU 协议，不暂存或覆盖用户未提交的 Excel，也不把产品 PDF 纳入提交。
