## 1. 文档目的

本文把“光谱仪 Windows 软件迁移到 Radxa ROCK 4B+”中真实遇到的问题、证据、根因、修复和边界整理成可复用方法。目标不是记录一串补丁，而是让下一次 Python + Qt、USB/串口、实时采集类软件迁移时，可以直接复用：

- 工作区保护方法；
- ARM64 环境与依赖决策；
- USB 识别和协议验证；
- 全帧采集、实时绘图与异步存储架构；
- SSH 远程部署和实机诊断；
- 证据驱动的性能与完整性验收。

配套的个人 Codex 技能源位于：

```text
codex-skills/rock4bplus-migration/
```

## 2. 项目背景与最终边界

目标平台：

| 项目 | 目标 |
|---|---|
| 板卡 | Radxa ROCK 4B+ |
| 操作系统 | Debian 12 Bookworm ARM64 |
| Python | 3.11 |
| 运行方式 | 源码 + venv |
| GUI | Qt，Linux 版最终使用 PyQt6 兼容层 |
| 光谱仪 USB | CH569W，VID:PID `1a86:fe0c` |
| 内核驱动 | `cdc_acm` |
| 设备节点 | 实机曾为 `/dev/ttyACM0`，但不作为永久身份 |
| 设备规模 | 第一阶段单台，架构保留最多约 4 台 |
| 部署目录 | `/opt/zgcai-spectrometer` |

项目维护边界：

- 原 Windows 项目与 Linux 版本分开维护；
- 只修改 Linux 专用副本；
- `deploy/rock4bplus` 只放发送到板端的运行内容；
- 项目文档、测试材料和个人技能不得混入部署载荷；
- 对 MCU 未发送或应用收到前已在 USB/内核链路丢失的数据不作不可能的保证；
- 对操作系统已交付给应用的合法数据，上位机尽最大能力完整解析、持久化并报告异常。

## 3. 最终架构概览

```text
CH569W 光谱仪
      │ USB CDC ACM
      ▼
独立采集进程
  串口读取 → 流式解码 → ACK/状态机 → 帧序号诊断
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
   追加式安全暂存主通道          容量为 1 的显示通道
   每个合法帧优先持久化          允许主动跳过旧帧
             │                       │
             ▼                       ▼
     独立导出进程              PyQtGraph/NumPy
     CSV / Excel               固定最高显示 FPS
             │                       │
             └───────────┬───────────┘
                         ▼
              状态、指标与飞行记录器
```

核心原则只有两条：

1. 数据保存通道完整优先，不被 GUI 绘制速度反向拖慢。
2. 显示通道展示“最新状态”即可，主动跳过必须计入显示指标，不能伪装成协议丢帧。

## 4. 迁移全过程中的问题与解决

### 4.1 工作区与 Git 保护

**现象**

Linux 副本中已经存在用户未提交的 Excel、Word 修改，以及 PDF、诊断包和采集数据。迁移任务又要求绝不能修改原 Windows 项目。

**证据**

开始前和每个大阶段都执行：

```powershell
git status --short
git diff --name-only
```

并确认当前绝对路径是：

```text
D:\codex\光谱仪 - Linux转移版
```

**排除项**

- 不把未提交内容当成迁移代码；
- 不使用会覆盖用户修改的恢复命令；
- 不用 `git add -A` 或无范围提交。

**根因**

迁移工作和用户现场资料共存于同一工作树，若缺少明确边界，自动格式化、部署生成或宽范围 Git 命令都可能误伤。

**修复**

- 建立受保护文件清单；
- 所有写入限定在 Linux 副本；
- 部署内容由显式清单生成；
- 每次只暂存本任务列明的文件；
- 提交前再次比较状态。

**验证结果**

原 Windows 项目未修改；用户已有 Excel、Word、PDF、诊断包和采集数据保持未覆盖、未删除、未误提交。

**通用经验**

迁移的第一项产物不是代码，而是“允许写什么、禁止写什么、哪些脏文件必须保存”的基线。

**适用边界**

适用于所有在现有工作区继续开发的任务，特别是实验数据与源码混放的项目。

### 4.2 ARM64 Python 与 Qt 依赖不兼容

**现象**

Windows 项目使用 PySide6，但目标是 Debian 12 ARM64、Python 3.11。直接按桌面环境的 pip 依赖思路无法得到稳定兼容的组合。

**证据**

板端验证了系统、架构和运行库：

```bash
cat /etc/os-release
uname -m
python3 --version
```

实际系统为 Debian 12、`aarch64`、Python 3.11。系统仓库能提供 PyQt6、QtSerialPort、NumPy、SciPy 等 ARM64 原生包。

**排除项**

- 没有为满足框架名称而强行使用不匹配的二进制 wheel；
- 没有立刻投入完整 Qt 交叉编译；
- 没有把开发机 x86_64 虚拟环境复制到 ARM64。

**根因**

Python wheel 的架构、Python ABI、glibc 和 Qt 二进制依赖必须同时兼容；“同版本 Python”不代表跨架构二进制可用。

**修复**

- 优先安装 Debian ARM64 原生 PyQt6 与 QtSerialPort；
- 建立 Qt 绑定兼容层，隔离 PySide6/PyQt6 的信号、枚举等差异；
- venv 使用 `--system-site-packages` 复用 apt 的原生 Qt 包；
- pip 只补充目标架构确实可用的依赖；
- 用导入测试确认 Qt、串口、NumPy、SciPy 和 Excel 库。

**验证结果**

板端 Qt 6.4.2、PyQt 6.4.2、NumPy、SciPy、QtSerialPort 和 Excel 库均可导入，程序能够显示主界面并连接实机。

**通用经验**

ARM64 上依赖来源优先级通常应为：目标发行版原生包 → 官方 ARM64 wheel → 源码构建 → 必要时交叉编译。

**适用边界**

若项目依赖仅存在于特定 Qt/PySide ABI、必须使用定制 Qt 模块或系统仓库版本过旧，再评估 Radxa 官方交叉编译流程。

### 4.3 SSH 中启动 GUI 直接 Aborted

**现象**

通过 SSH 执行 `/opt/zgcai-spectrometer/run.sh` 后程序输出 `Aborted`。

**证据**

```text
DISPLAY=<empty>
XDG_SESSION_TYPE=tty
qt.qpa.xcb: could not connect to display
Could not load the Qt platform plugin "xcb"
```

**排除项**

Qt `xcb` 插件本身已经存在，因此不是简单的“插件文件缺失”；主界面后来能从板端桌面正常启动，也排除了程序入口完全损坏。

**根因**

普通 SSH tty 没有连接到板端图形会话，缺少 `DISPLAY` 与对应认证环境。Qt 找到 `xcb` 插件，但无法连接显示服务。

**修复**

- GUI 从 ROCK 4B+ 桌面快捷方式或本地图形终端启动；
- SSH 用于日志、进程、性能、USB 和安装操作；
- 无界面渲染测试显式使用 `QT_QPA_PLATFORM=offscreen`。

**验证结果**

板端主界面成功显示；SSH 仍可并行执行性能和日志命令。

**通用经验**

“程序在 SSH 中启动失败”不等于“Qt 安装失败”。先检查会话类型和 `DISPLAY`。

**适用边界**

如果明确启用了 X11 转发或远程桌面，可从远端启动 GUI，但延迟和渲染路径不同，不能替代本地显示验收。

### 4.4 USB 设备身份与 udev 权限

**现象**

系统通过 `cdc_acm` 把设备识别为 `/dev/ttyACM0`。需要自动识别，并考虑以后接入多台同型号 CH569W 光谱仪。

**证据**

`lsusb` 显示 `1a86:fe0c`，`lsusb -t` 显示 CDC Communications/Data 接口，设备节点存在，用户属于 `dialout`。

**排除项**

- `1a86:fe0c` 不是一台物理光谱仪的唯一身份；
- `/dev/ttyACM0` 也不是永久身份，拔插和枚举顺序会改变编号；
- 不能只凭端口能打开就认定是受支持光谱仪。

**根因**

VID:PID 只标识一类 USB 实现；同型号设备共享 VID:PID，串口节点由枚举顺序分配。

**修复**

识别采用三层条件：

1. VID:PID 筛选候选串口；
2. 发送版本查询并验证协议响应；
3. 使用设备返回的生产序列号作为业务身份。

udev 规则使用最小权限和 `dialout`，不设置全局 `0666`，也不为多台相同设备创建冲突的公共固定链接。

**验证结果**

程序能自动显示 `/dev/ttyACM0` 光谱仪、SN003、软件版本 2.20、硬件版本 1.20 和 3648 个有效像素。

**通用经验**

USB 身份应是“总线候选 + 协议握手 + 设备序列号”，不能只看 VID:PID 或 tty 名。

**适用边界**

若固件没有唯一序列号，只能再结合 USB 拓扑端口或人为配置，无法凭相同 VID:PID 自动区分物理设备。

### 4.5 实机协议与文档存在两个兼容格式

**现象**

函数表描述新格式为 U32 包号，但旧设计记录又说明部分固件使用 U16 包号，且长度是否包含校验字节不同。错误选择会造成整条流错位。

**证据**

使用串口调试助手执行单帧采集，结合实机握手参数和十六进制流确认：

- 总像素数 `nPixel = 3694`；
- 有效区起点 32，有效像素 3648；
- 实机数据帧使用旧兼容格式 U16LE 包号；
- `nLength = 3 + 2*nPixel = 7391`；
- 物理总长度 `4 + nLength = 7395`；
- 该格式的校验字节不计入 `nLength`；
- 像素值为 U16 大端；
- 数据帧校验字节为任意值，应消费但不验证。

同时保留新格式：

```text
0x24 | nLength(U16LE) | 0x80 | nPacketNumb(U32LE) | Data(U16BE) | Checksum
nLength = 6 + 2*N
物理总长 = 3 + nLength
```

**排除项**

- 不依据记忆删除 U32 格式；
- 不通过连续采集才能证明长度，单帧已经能提供完整边界；
- 不把数据帧的任意校验规则套用到普通控制帧。

**根因**

实机固件存在兼容协议版本，包号宽度和长度语义不同；协议文档只描述一种格式会造成误判。

**修复**

- 解码器保留 U16LE 和 U32LE 两种数据帧候选；
- 握手后用像素数约束合法长度；
- 像素统一按 U16BE 解析；
- 数据帧消费校验字节但不比较数值；
- 普通控制帧继续按其自身长度与校验规则处理。

**验证结果**

单帧十六进制证据与程序解析公式一致，实机能够稳定识别和连续接收。

**通用经验**

协议不明确时，用“握手元数据 + 单帧原始字节 + 物理总长”验证长度语义；不要先猜校验。

**适用边界**

若以后出现第三种固件格式，应新增受严格命令、长度和像素数约束的候选，不能放宽为任意大长度。

### 4.6 校验错误、拒绝候选帧与 ACK 超时

**现象**

初版运行中出现大量“校验码错误”和“拒绝候选帧”，随后停止命令 `0x52` ACK 超时；再次开始时 `0x21` 触发模式配置 ACK 超时，最终无法采集。

**证据**

诊断记录曾出现：

```text
期望 0x14，收到 0x07
期望 0x5F，收到 0xEE
设备命令 0x52 ACK 超时
设备 0 命令 0x21 ACK 超时
```

系统层 `dmesg` 没有同期 USB reset、disconnect 或 overflow；CPU 和内存也没有耗尽。

**排除项**

- 不是简单的 USB 线断开；
- 不是主板整体 CPU 满载导致内核丢设备；
- 不能靠忽略所有校验或每次错误重置串口解决；
- 像素数据中也可能出现 `0x24`，不能见头字节就接受候选。

**根因**

流式解码器把数据负载中的 `0x24` 当作新帧头，并允许不受像素数约束的伪长度。错误候选导致缓冲区错位，控制 ACK 也被吞入错误的数据帧路径，最终状态机超时。

**修复**

- 普通帧与 `0x80` 数据帧分开计算物理长度；
- 数据帧候选必须同时匹配命令码、握手像素数和已知兼容格式；
- 拒绝伪候选时只推进一个字节，再继续搜索；
- 普通控制帧继续验证校验；
- 数据帧校验字节只消费、不比较；
- 解码器向设备管理器注入期望像素数；
- ACK 和数据共用有确定边界的流式分包机制。

**验证结果**

更新后连续采集能够正常启动和停止，拒绝/重新同步显著归零；后续诊断包在完整采集阶段显示缺帧、拒帧和重新同步均为 0。

**通用经验**

串口协议的“重新同步”必须依赖严格候选边界。放宽长度看似兼容，实际上会让任何负载字节劫持整个数据流。

**适用边界**

如果底层驱动真实丢字节，严格解码器只能恢复到下一个合法边界并报告缺口，不能重建丢失字节。

### 4.7 起初只有 2–4 FPS，运行后越来越慢

**现象**

刚开始采集最多约 2 FPS，随后降到零点几，采集一段时间后曲线停住。开启自动保存更严重。

**证据**

- 诊断页显示 10 秒可收到约 900 帧，说明设备实际约 90 FPS；
- `top -H` 显示 Python 主进程和 QThread 占用接近一个 CPU 核，但系统仍有约 75%–80% 总体空闲；
- 内存有余量，无 swap 压力；
- 温度和 `dmesg` 无明显 USB 异常；
- 切到诊断页后卡顿明显消失。

**排除项**

- 不是四核 CPU 整体性能完全不足；
- 不是显示器分辨率单独导致，因为页面切换立即改变负载；
- 不是光谱仪只发 2–4 FPS；
- 离屏绘图约 25–27 ms 也不能单独解释真实 UI 只有 3–4 FPS。

**根因**

采集、解析、绘图和部分存储工作耦合在同一 Python/Qt 运行路径；高频帧触发大量 GUI 更新与 Python 对象创建，事件队列堆积，运行时间越长越严重。

**修复**

- 分离完整采集速率和显示速率；
- 让显示通道只保留最新帧；
- 用固定定时器驱动绘图；
- 将持久化和导出移出 GUI；
- 后续进一步替换绘图后端。

**验证结果**

采集不会再因绘图积压停住；完整帧持续约 90 FPS，显示按照板端能力独立调优。

**通用经验**

“程序占一核、系统还有空闲”是典型 Python GUI 串行热点，不等于整机算力耗尽。先分层测速率。

**适用边界**

若采集解析本身也需要超过单核能力，仍需使用进程、原生扩展或降低设备数据率；显示节流不能解决真实解码不足。

### 4.8 “缺失多帧”其实是显示节流误报

**现象**

绘图约 4 FPS 时诊断页偶尔显示缺失多帧，看起来像 USB 或串口丢帧。

**证据**

诊断包中：

- 完整帧率约 89.9 FPS；
- 持久化帧率约 89.9 FPS；
- 解码器真实 missing、reject、resync 为 0；
- 日志却在经过节流的显示帧上反复报告“缺失 4 帧”。

**排除项**

- 不是设备协议序号真实连续缺口；
- 不是持久化漏帧；
- 不是 USB 内核错误。

**根因**

序号追踪被错误放到了显示抽样链路。为限制绘图 FPS，程序主动跳过中间帧，但追踪器把这些有意不显示的帧当作协议丢失；重复的显示节流还造成日志洪泛。

**修复**

- 只在完整解码主通道判断协议序号；
- 显示通道记录 `intentional_skipped`；
- 删除重复节流，只保留一个明确的显示频率控制点；
- 诊断页面分别显示接收、持久化、显示和主动跳过。

**验证结果**

真实缺帧统计归零，诊断不再因显示降采样误报；显示仍可低于设备帧率。

**通用经验**

任何下采样、去抖或容量 1 队列之后的序号都不能用于判断源数据完整性。

**适用边界**

如果设备不提供可靠序号，只能证明应用完整帧与持久化记录的关系，不能证明 MCU 发送前是否缺帧。

### 4.9 QPainter 绘图成为真正瓶颈

**现象**

修正采集链路后，绘图区仍只有约 4 FPS；切换到诊断页流畅。

**证据**

一次诊断包给出的分层结果大致为：

| 指标 | 结果 |
|---|---:|
| 完整/持久化 | 约 89 FPS |
| 显示发布 | 约 17.75 FPS |
| 实际绘制 | 约 3.64 FPS |
| 实时页主进程 CPU | 约 98.6% 单核 |
| 诊断页 CPU | 约 32.7% |

旧实现使用 QPainter，并在每次绘制构造大量 Python `QPointF` 等对象。

**排除项**

- 不是串口只有 4 FPS；
- 不是显示发布只有 4 FPS；
- 不是存储卡住；
- 不是只调显示器或强制 OpenGL 就一定能解决。

**根因**

Python 层逐点构造和自绘坐标轴的成本超过 ROCK 4B+ 单核可承受范围，真实 paint 事件成为瓶颈。

**修复**

- 使用 Debian 提供的 PyQtGraph；
- 曲线使用连续 NumPy 数组并复用 `PlotDataItem.setData`；
- 使用 peak downsampling 保留峰值形态；
- 固定显示定时器，避免每帧直接绘制；
- 未验证驱动稳定前不启用 OpenGL；
- 逐步从较低显示频率调到 25 FPS 上限，即 40 ms 间隔。

**验证结果**

中间版本实际绘制约 17.6 FPS；最终实机约 22.5 FPS，同时完整/持久化仍约 90 FPS，停止正常，缺帧、拒帧和重新同步为 0。

**通用经验**

绘图库不是抽象偏好，而是嵌入式平台性能架构的一部分。数组化、对象复用和峰值降采样通常比微调 QPainter 更有效。

**适用边界**

最终 FPS 仍受曲线数量、像素数、窗口尺寸、坐标轴更新和桌面合成器影响。25 FPS 是本实机选择，不是所有 ROCK 4B+ 项目的固定答案。

### 4.10 所有采集数据必须保存

**现象**

用户要求任何情况下尽可能读到完整、正确的数据，所有上位机收到的合法采集帧都必须保存，同时界面尽可能流畅。

**证据**

设备约 90 FPS，而 GUI 的可接受绘制速度远低于该值。若让 GUI 或 Excel 写入反向阻塞串口，数据完整性无法成立。

**排除项**

- 不能用“只处理显示帧”代表全部数据；
- 不能用无界内存队列暂存全部历史；
- 不能因为界面跟不上就静默丢弃采集帧；
- 不能承诺恢复 MCU 没发的数据。

**根因**

数据完整性和交互流畅性是两种不同服务等级，必须在架构上分通道处理。

**修复**

- 独立采集进程独占串口、解码、ACK 和协议状态机；
- 每个合法帧先写追加式安全暂存；
- 显示通道容量为 1，只展示最新帧；
- 导出进程从暂存生成 CSV/Excel；
- 有界队列必须有可观察的背压策略；
- 停止时先停止设备、收尾尾帧，再安全关闭暂存；
- 对每层计数并写入飞行记录器。

**验证结果**

完整采集和持久化可维持约 90 FPS，同时绘图以约 22.5 FPS 独立运行。显示跳过不再影响存储。

**通用经验**

全帧要求的正确架构是“主数据通道可靠、显示旁路可丢旧帧”，而不是强迫 GUI 画出每一帧。

**适用边界**

当磁盘持续写入速度低于合法数据率时，任何有限存储最终都会耗尽。必须监控磁盘、暂存写入错误和容量阈值，并明确停止策略。

### 4.11 自动保存导致界面卡顿和停止缓慢

**现象**

启用自动批量保存后，采集中整个界面卡顿；停止时 CSV/Excel 收尾很久。

**证据**

生成的 CSV/XLSX 体积较大；运行越久停止越慢，说明收尾工作与帧数相关。未自动保存时也有部分处理链工作与 GUI 耦合。

**排除项**

- 不是简单把批次从 500 改小就能根治；
- 不是只优化 Excel 格式即可；
- 不能在停止按钮回调中同步完成所有数据转换。

**根因**

频繁写表格、批量格式转换和最终 Excel 构建占用 GUI/共享 Python 执行路径；停止操作等待导出完成。

**修复**

- 采集时只做固定成本的追加式暂存；
- CSV/Excel 由独立导出进程异步生成；
- 采集开始时冻结处理配置快照，保证整批语义一致；
- 停止设备与导出完成状态分离；
- 先写临时文件，成功后原子重命名；
- 导出失败立即释放采集状态并保留可恢复暂存。

**验证结果**

停止采集不再等待完整 Excel 收尾，GUI 保持可操作；成功导出后清理暂存，失败时给出可恢复路径。

**通用经验**

Excel 是结果格式，不应成为实时数据总线。实时阶段应使用追加写、固定成本和可恢复格式。

**适用边界**

导出仍可能消耗 CPU 和磁盘，低速存储介质上应限制并发导出数量并展示进度。

### 4.12 偶发高强度值与错误帧判断

**现象**

正常强度在几千左右，偶尔出现几万；又担心背景扣除后大量接近 0 的值被误判成错误帧。

**证据**

协议数据是 U16 原始值，合法范围可到 65535。暗场、饱和、背景变化、真实光脉冲都可能形成极低或极高值；背景扣除会产生 0 或负浮点数。

**排除项**

- 不以“高于经验阈值”直接删除帧；
- 不以“同帧大量接近 0”直接判错；
- 不在背景扣除后做原始结构校验；
- 不用插值或平滑伪造丢失帧。

**根因**

数值异常与协议结构错误是两个维度。单纯强度阈值无法区分真实信号、饱和、暗场和错位解析。

**修复**

正确性判断顺序：

1. 先校验帧头、命令、长度、像素数和物理边界；
2. 再解析原始 U16；
3. 记录可疑统计但保留结构合法帧；
4. 按冻结配置执行背景扣除、强度校准或 airPLS；
5. 绘图和导出均使用同一最终处理结果；
6. 用户确认扣背景时只保留扣除后的结果，允许负值。

**验证结果**

背景扣除不会因大量零值触发错误帧规则；导出与绘图处理语义一致，可疑强度仍能在诊断中追踪。

**通用经验**

原始协议完整性校验必须早于任何科学计算。数值异常默认“保留并标记”，除非领域规则和实验证据足以证明损坏。

**适用边界**

如果传感器有明确硬件饱和码、坏像素表或固件错误标志，可追加领域级质量标记，但仍应保留原始证据。

### 4.13 未勾选自动保存仍出现 zgs

**现象**

自动批量存储未勾选，但采集后仍生成 `.zgs` 文件，用户认为程序在偷偷保存正式数据。

**证据**

`.zgs` 来自全帧安全暂存链路，不是用户选择的 CSV/Excel 正式输出。旧生命周期没有在正常无自动保存路径清理它。

**排除项**

- 不能取消安全暂存，否则全帧保证和崩溃恢复能力下降；
- 不能让内部缓存永久混在正式数据目录；
- 不能仅改扩展名掩盖语义。

**根因**

内部可靠性文件和用户正式输出的生命周期没有明确分离。

**修复**

- 无自动保存且正常结束：清理 `.zgs`；
- 自动保存成功：CSV/XLSX 原子完成后清理 `.zgs`；
- 导出失败或异常终止：保留 `.zgs`，诊断页明确报告路径；
- 启动时扫描可恢复暂存；
- 不把 `.zgs` 当作普通历史文件展示。

**验证结果**

更新验证显示未勾选自动保存时不再新增正式文件或残留正常暂存；开启自动保存时按策略生成 CSV/XLSX。

**通用经验**

安全缓存可以始终存在于运行过程，但必须有清晰、可测试、对用户透明的生命周期。

**适用边界**

断电或强制杀进程可能留下暂存，这属于预期恢复行为，不应自动无条件删除。

### 4.14 诊断记录难以远程传递

**现象**

最初只能由用户手工复制诊断页文本，难以准确判断长期采集、帧率、误报与程序版本。

**证据**

同一现象需要多次截图、`top` 输出和手工日志才能拼出时间线；后来诊断 ZIP 能直接证明完整帧率、持久化率、绘制率和错误计数。

**排除项**

- 不无限提高普通文本日志等级；
- 不把全部正式光谱数据默认打包；
- 不只记录最终错误而丢失故障前状态。

**根因**

缺少低开销、结构化、可导出的运行证据。

**修复**

增加飞行记录器与诊断包：

- 状态机时间线；
- 分层帧率；
- 队列水位；
- 序号/拒绝/重同步计数；
- CPU、内存、温度和磁盘摘要；
- 版本、启动命令和部署哈希；
- 最近少量帧样本；
- ZIP 清单与哈希。

**验证结果**

通过最新诊断包可直接定位“采集约 90 FPS、绘图约 4 FPS”的真实瓶颈，并验证后续约 22.5 FPS 和零缺帧结果。

**通用经验**

飞行记录器不是调试日志堆积，而是有界、结构化、面向故障前后证据的黑匣子。

**适用边界**

高频原始数据仍需限制采样数量，避免诊断机制本身改变实时性能。

### 4.15 SSH、SCP 与安装命令混用

**现象**

曾在板端 SSH Bash 中运行 Windows 的：

```text
scp ".\deploy\rock4bplus\..."
```

出现 `command not found`；也曾执行：

```text
cd ~/home/radxa/rock4bplus-storage-fix/install.sh
```

导致路径错误。

**证据**

终端提示 Bash 把第二个 Windows 路径当作命令；`find` 已显示脚本是 `/home/radxa/rock4bplus-storage-fix/install.sh`，但 `cd` 目标既重复了 `/home/radxa` 又指向文件。

**排除项**

- 不是 `scp` 服务不可用；
- 不是脚本缺失；
- 不是需要重新安装 SSH。

**根因**

开发机 PowerShell 和板端 Bash 的命令职责、路径语法没有被明确区分。

**修复**

- 上传/下载 `scp` 在 Windows PowerShell 执行；
- `sudo install`、`apt`、`dmesg` 在 SSH Bash 执行；
- 先 `cd` 到目录，再执行 `sudo ./install.sh`；
- 含中文或空格路径分别加引号；
- Windows 下载目标优先写完整文件路径，避免尾部反斜杠引号歧义。

**验证结果**

文件可正确上传、安装，诊断 ZIP 也能从板端下载到 Windows。

**通用经验**

任何给用户的远程操作说明都必须在命令前标注“Windows PowerShell”或“ROCK 4B+ SSH”。

**适用边界**

其他宿主系统只需替换路径语法，主机职责分离原则不变。

### 4.16 部署副本容易与源码漂移

**现象**

开发中多次增量上传单个 Python 文件，存在源码已修复但 `deploy/rock4bplus` 或板端仍运行旧版本的风险。

**证据**

曾用源码常量和进程启动时间核对板端实际版本；只有看到 `FRAME_EMIT_INTERVAL_NS = 50_000_000` 和启动命令，才能确认更新生效。

**排除项**

- 不能用“复制命令无报错”证明板端运行的是新代码；
- 不能手工长期维护两套同名源码；
- 不能把整个项目无选择传到板端。

**根因**

运行部署副本是第二份文件树，手工复制天然容易遗漏或夹带。

**修复**

- `deploy/rock4bplus` 只保留板端运行文件、依赖、安装/启动脚本、udev 和桌面入口；
- 用 `tools/build_rock4bplus_deploy.py` 从源码生成；
- 用 `--check` 比较部署清单与哈希；
- 安装后通过源码标记、启动时间、命令和诊断清单核对。

**验证结果**

部署检查最终覆盖 76 个文件且一致；知识文档和个人技能未进入部署载荷。

**通用经验**

部署目录应是“可再生构建产物”，不能是人工维护的第二源码仓库。

**适用边界**

若改用 Debian 包、容器或镜像，仍要保留构建清单、哈希和板端版本证明。

### 4.17 CSV、Excel、处理链和交互补齐

**现象**

Linux 版迁移完成核心采集后，还需要补齐 Windows 版已有的强度校准、airPLS、保存策略、中文标签和绘图交互。

**证据**

用户提供了模拟多设备 CSV/Excel 样例，并明确最终规则：

- CSV+Excel 模式：单设备导出 CSV，多设备导出一个 Excel；
- 纯 CSV：每台设备一个 CSV；
- 命名规则保持；
- 表格标签中文；
- 强度校准采用已确认的 A 方案；
- airPLS 与处理结果进入显示和存储同一链路；
- 禁用滚轮和右键缩放，只保留框选放大和双击还原。

**排除项**

- 不让绘图使用处理后数据而导出使用原始数据；
- 不破坏历史文件读取；
- 不为单设备在 CSV+Excel 模式同时生成两个格式；
- 不覆盖既有同名文件。

**根因**

平台迁移不只包含“能启动”，还需要恢复产品级行为一致性；处理链、格式策略和交互都必须纳入验收。

**修复**

- 统一处理管线和冻结配置快照；
- 背景扣除、强度校准、airPLS 后的最终数组同时进入绘图与导出；
- 按设备数量和用户模式选择 CSV/XLSX；
- 本地化元数据与标签，同时兼容旧英文历史文件；
- Excel 一个设备一个工作表；
- 保持每帧一列、每像素一行；
- 文件重名追加后缀，不覆盖；
- 通过 Qt/PyQtGraph 交互配置屏蔽滚轮和右键缩放。

**验证结果**

导出策略和内容符合用户确认的样例；单设备不再因 CSV+Excel 模式同时生成两类文件；交互和中文标签按要求完成。

**通用经验**

迁移验收要覆盖行为语义，不应只比较类名和界面外观。处理结果在显示、缓存、导出和历史页之间必须一致。

**适用边界**

如果未来加入新的处理方式或格式，需要为配置版本、历史读取和批次冻结语义增加兼容测试。

### 4.18 Windows 中文参数与工具编码

**现象**

创建配套个人技能时，官方初始化器返回成功，但通过命令行参数生成的中文
`agents/openai.yaml` 不是有效 UTF-8；随后官方校验器又因当前 Anaconda 默认
使用 GBK 读取 UTF-8 中文 `SKILL.md` 而报 `UnicodeDecodeError`。

**证据**

- 初始化器已创建文件且退出码为 0，但补丁工具无法按文本读取该 YAML；
- 精确检查后确认只有新生成的 221 字节元数据文件编码异常；
- 重新以 UTF-8 创建 YAML 后内容正常；
- 使用 `python -X utf8 ...quick_validate.py` 后返回 `Skill is valid!`。

**排除项**

- 不是技能 frontmatter 或链接结构错误；
- 不是把整个技能目录删除重建；
- 不是把中文全部改成英文来回避问题。

**根因**

Windows 控制台、Python 默认文本编码和工具的参数/文件写入编码不一致。工具退出成功只证明流程完成，不证明生成文件能按目标编码读取。

**修复**

- 对新生成的元数据立即做 UTF-8 回读；
- 只删除已确认异常且刚生成的精确文件，再用补丁以 UTF-8 重建；
- 运行 Python 文本工具时显式使用 `-X utf8`；
- 把生成后验证作为正式流程，而不是相信退出码。

**验证结果**

技能 YAML、`SKILL.md` 和全部中文参考文件均可按 UTF-8 读取，官方校验器通过。

**通用经验**

含中文路径、参数或元数据的 Windows 工具链要分别验证“命令参数编码、文件编码、读取默认编码”。生成成功后必须回读。

**适用边界**

在默认已启用 UTF-8 的 Python 环境中不需要 `-X utf8`，但显式指定仍能提高跨机器可复现性。

## 5. 被否定或限制使用的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 禁用所有帧校验 | 否定 | 会让普通控制帧失去完整性保护，只解决表象 |
| 每次解析错误就重置串口 | 否定 | 破坏连续流并导致更多 ACK/状态机问题 |
| 用强度阈值删除异常帧 | 否定 | 暗场、饱和、背景扣除和真实脉冲可能合法 |
| 只隐藏缺帧警告 | 否定 | 不修正错误统计来源，掩盖真实问题 |
| GUI 线程同步写 CSV/Excel | 否定 | 会造成事件循环卡顿和停止时间随数据增长 |
| 仅降低显示 FPS | 受限 | 可缓解负载，但不解决旧 QPainter 的逐点开销 |
| 强迫 GUI 显示每个设备帧 | 否定 | 与全帧保存目标冲突，显示不应成为背压源 |
| 无界队列保存全部帧 | 否定 | 只是把故障推迟到内存耗尽 |
| 直接交叉编译整套 Qt | 暂不采用 | Debian ARM64 原生包已满足需求，成本收益不合适 |
| 默认启用 OpenGL | 暂不采用 | 驱动与实际稳定性未经验证，软件渲染已达目标 |
| VID:PID 或 tty 名作为唯一身份 | 否定 | 同型号设备共享 VID:PID，tty 编号会变化 |
| 正常结束后永久保留 `.zgs` | 否定 | 内部安全缓存不应成为意外用户输出 |
| 只看离屏基准判断 UI 性能 | 否定 | 不包含实际事件循环、坐标轴和桌面合成路径 |

## 7. 可复用的标准迁移流程

### 阶段 1：冻结边界

1. 确认源项目与迁移副本的绝对路径。
2. 记录 Git 状态和受保护文件。
3. 明确部署目录允许包含的文件类别。
4. 禁止宽范围清理、覆盖和暂存。

### 阶段 2：建立目标环境事实表

1. 在实机采集 OS、架构、Python、Qt、显示会话、用户组、USB、内核和磁盘事实。
2. 把产品简介作为硬件背景，不替代运行时探测。
3. 建立依赖来源与风险矩阵。

### 阶段 3：做最小迁移设计

1. 分出平台无关域逻辑和平台适配层。
2. 决定 Qt 绑定策略。
3. 决定设备身份、权限与重连策略。
4. 先画清实时数据、显示和存储通道。
5. 定义可测量验收指标。

### 阶段 4：先打通最小实机闭环

按顺序验证：

```text
枚举 → 握手 → 参数读取 → 单帧原始字节 → 连续采集
→ 停止 → 再次开始 → CSV → Excel → 拔插重连
```

在协议未证实时，不先做大规模 UI 优化。

### 阶段 5：按层定位问题

```text
设备/USB → 内核/tty → 串口读取 → 流式解码 → 协议状态机
→ 持久化 → 处理链 → 显示发布 → 实际绘制 → 导出
```

每层都需要独立计数、速率和失败原因。

### 阶段 6：设计全帧与流畅并存

1. 采集进程优先保存所有合法帧。
2. 显示队列只保留最新帧。
3. 协议缺帧只在完整主通道判断。
4. 导出在独立进程完成。
5. 所有队列有界且有监控。

### 阶段 7：证据驱动调优

1. 对比实时页和非绘图页 CPU。
2. 对比接收、持久化、发布和绘制 FPS。
3. 优化最大热点，而不是先猜处理器或显示器。
4. 每次只改变一个主要变量。
5. 用同一诊断包指标验证前后差异。

### 阶段 8：可恢复部署

1. 由构建脚本生成板端载荷。
2. 在 Windows 上传，在板端安装。
3. 用桌面会话启动 GUI。
4. 用 SSH 做运维和诊断。
5. 记录版本、哈希和回滚单位。

### 阶段 9：验收与沉淀

1. 执行功能、性能、完整性、断线、停止和导出矩阵。
2. 保存诊断包作为证据。
3. 把问题按统一模板复盘。
4. 只把已证明、可泛化的方法提升到技能。

## 9. 已知保证边界

本项目上位机能够承诺：

- 对成功进入应用串口读取层的字节进行尽可能可靠的流式分包；
- 只接受与协议命令、长度和握手像素数一致的数据帧；
- 对每个合法帧优先持久化；
- 报告可观察到的序号缺失、重复、乱序、解析拒绝和存储失败；
- 让显示降采样不影响主数据保存；
- 在正常停止、导出失败和应用异常时保留足够恢复证据。

本项目不能承诺：

- 恢复 MCU 没有发送的帧；
- 恢复 USB 控制器、内核或驱动在应用读取前已经丢失且没有任何可用副本的数据；
- 在磁盘永久写满或硬件持续故障时无限缓存；
- 仅凭强度数值判断每一帧的物理真实性；
- 在所有显示器、桌面合成器和未来依赖版本上固定达到 25 FPS。

保证边界必须在产品验收中明确，否则“任何情况下完整”会变成无法证明的要求。
